# Follow-ups for the x86-64 machine

The aarch64 port was done on an M1 Max, which cannot run x86-64. Throughout it x86-64 compiled, and
its generated routines stayed byte-identical, but nothing has run there since `8311e28`. These are
for the Ryzen 9 9950X, roughly in this order. Delete an item when it is done, and put what it found
in the note on its topic.

## Does it still work?

Run `scripts/heavy scripts/gate`, then `scripts/gate --all`, `lean/scripts/check.sh` (`lake` needs
elan), `scripts/preload-check` and the soak.

Things that changed there, and should show nothing or a small improvement:

- **`scripts/cpusets`** now derives the CPU sets from sysfs. Only fixture tests have checked the Ryzen:
  it should print 0-3 and 8-11 for the two domains, 2 for single-threaded jobs, 12-15,28-31 for heavy
  work and 15 for the runner.
- **`collect`** could leave blocks parked on a CPU a thread left partway through (`f3d4c94`).
- **Cache domains:** a machine where no two CPUs share the last listed cache now has one domain
  (`a39d1c7`). Zen 5 should still find two.
- **The C frees' mirror** is not published for a heap whose base index is under the region count
  (`5e7730c`), and region `r` has entry `r + 1` of its table, so that a sized free of null finds no
  class. A free of a region numbered 2047 now wraps round the page, where 2048 did.
- **Large slots** are rounded up to a page before the class is found. That changes no class on 4 KiB
  pages by reasoning, with a test on the design's geometry.
- **The rules in `back/policy.rs`** are stated in bytes, with compile-time asserts that they keep their
  values on `Geometry::DESIGN`.
- **The dense launder and fill** (`53f9b15`) are generic code. They do the same work in fewer
  instructions, and took 4.6% off the tree job on the M1. Fuzzing and the back end's tests cover them,
  but they have not run here, and Zen 5's numbers will differ.
- **The binary:** slow paths grew about 0.5% and then 0.28% of text, while the routines and C entry
  points kept their size. Any size change moves where a program's code lands, so a job that moves
  needs a placement sweep before it is read (`docs/research/measuring.md`).

## Correct the standings

`bench/Cargo.toml`'s release profile sets `debug = 1`, which allocator crates read as a request. So on
this machine `snmalloc-sys` built snmalloc's Debug configuration, and `cc` gave the C of the
jemalloc and mimalloc crates frame pointers. The profile now overrides this (`69dd363`, `d8653d1`).

- Every snmalloc figure in the notes is that Debug build, including the "best of eight" comparisons
  and the server rates set from "slowest snmalloc", which may need setting again.
- jemalloc and mimalloc had the smaller handicap. Rerun them with `bench/standings/README.md`, and
  see whether cralloc's lead on servers (`docs/research/standings.md`) holds, and by how much.
- Claims about snmalloc in `docs/research/servers.md` were removed rather than corrected. Restore
  what the rerun supports.

## Does the page stagger help here?

Large blocks on aarch64 are staggered by whole pages as well as by lines, because slots a power of two
of pages apart land in one TLB set. On the M1 at 16 KiB pages, 64 buffers written in turn run at 0.46 to
0.53 ns an element with it and 0.95 to 7.6 without. x86-64 has P = 0, so the page term is off.
Zen 5's L2 TLB also indexes by low page-number bits (`docs/research/hardware.md`), so it may help, and
it costs only address space: at most an eighth of a slot. The lines alone already brought Zen 5 from 7.9
to about 0.8 ns on one such job, so the gain may be small.

`bench/roofline/machine` is aarch64-only, so its `streams rule` probe needs porting, or test by turning
the page term on through the real allocator with 64 large buffers written in turn. Adopt it only if it
wins here, and remember that `Geometry::DESIGN` and its asserts then change.
